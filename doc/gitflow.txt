1. INTRODUCTION                                               *gitflow-intro*

Gitflow is a Neovim plugin that provides a unified interface for local git
operations and GitHub workflows. It includes panels for status, branches,
diffs, logs, stashes, issues, pull requests, code review, conflict
resolution, labels, and a command palette.

==============================================================================
2. REQUIREMENTS                                        *gitflow-requirements*

- Neovim >= 0.9
- git
- gh (GitHub CLI), authenticated

==============================================================================
3. INSTALLATION                                        *gitflow-installation*

lazy.nvim: >lua
    {
      "devGunnin/gitflow",
      config = function()
        require("gitflow").setup()
      end,
    }
<

packer.nvim: >lua
    use {
      "devGunnin/gitflow",
      config = function()
        require("gitflow").setup()
      end,
    }
<

Manual: >sh
    git clone https://github.com/devGunnin/gitflow.git \
      ~/.local/share/nvim/site/pack/plugins/start/gitflow
<

Then add `require("gitflow").setup()` to your init.lua.

==============================================================================
4. SETUP                                                      *gitflow-setup*

Call `setup()` to initialize the plugin with optional configuration: >lua
    require("gitflow").setup({
      -- configuration table (see |gitflow-config|)
    })
<

All configuration fields are optional and fall back to built-in defaults.

5. CONFIGURATION                                             *gitflow-config*

                                                   *gitflow-config-keybindings*
keybindings ~

Table mapping action names to normal-mode key sequences. Override any global
keybinding by specifying the action name and desired mapping: >lua
    keybindings = {
      status = "<leader>gs",
      commit = "<leader>gc",
    }
<
These are ordinary normal-mode mappings installed in every buffer, so they are
opt-out at two grains.  Set one action to `false` to leave that key alone: >lua
    keybindings = { commit = false }
<
Or set the whole table to `false` to install none of them.  The <Plug> targets
below are still defined, so you can bind your own keys to any action: >lua
    require("gitflow").setup({ keybindings = false })
    vim.keymap.set("n", "<leader>c", "<Plug>(GitflowCommit)", { remap = true })
<
A duplicate mapping is an error; a disabled action claims no key and so cannot
collide.  See |gitflow-keymaps-v2| for what moved in v2 and how to restore it.

                                            *gitflow-config-panel-keybindings*
panel_keybindings ~

Per-panel key overrides (issue #307).  Keyed by the panel's registry name,
then by the DEFAULT key label that panel advertises; the value is the
replacement key, or `false` to unbind it entirely: >lua
    panel_keybindings = {
      status = { X = "<leader>X" },   -- move "discard changes"
      tag    = { D = false },         -- remove "delete tag"
    }
<
Panel names and their key labels are exactly what `?` lists inside the panel,
and what KEYBINDINGS.md documents.  An override moves the hint and the `?`
entry with the binding, so the panel never advertises a key it does not bind.
This covers every registered surface, including the three that are not panels
(actions, conflict_resolver, review_diff) and the command palette.

A pair or range entry (`s/u`, `p/w/e/s/f`, `1-9`) can be re-keyed whole: name
several keys separated by `/`.  A single key collapses the entry to that key.
>lua
    panel_keybindings = {
      rebase = { ["p/w/e/s/f"] = "p/r/e/s/f", r = "R" },  -- r rewords again
    }
<
Two guards, both loud.  A label that matches no key in that panel warns when
the panel opens.  An override that would land on a key the panel already binds
is REFUSED whole for that panel, with a warning naming the clash -- otherwise
one verb silently wins the key while the hints advertise both.  Move the other
key in the same table, as `r = "R"` does above, and both apply.

                                               *gitflow-config-inline-blame*
inline_blame ~

    Current-line inline blame: shows "<author>, <date> * <summary>" as
    virtual text at the end of the line under the cursor.  Toggle it per
    buffer with `:Gitflow blame-inline` (default <leader>gB), or set
    inline_blame.auto to show it in every file automatically.  (Distinct
    from `:Gitflow blame` / gB, which opens the full blame panel.)

    Option          Type        Default         Description ~
    enable          boolean     true            Master switch; false disables
                                                the feature entirely
    auto            boolean     false           Auto-show in every file buffer
    delay           number      200             Debounce (ms) before blaming
    date_format     string      "%Y-%m-%d"      os.date() format for the date

                                                    *gitflow-config-actions*
actions ~

    Option              Type        Default     Description ~
    watch_interval      number      10000       Poll interval (ms) for the
                                                 actions panel's live-watch
                                                 (`w`); minimum 1000

                                                  *gitflow-config-validation*
validation ~

    setup() rejects a config it cannot honour instead of ignoring it.

    Unknown options raise an error naming the full path, with a suggestion
    when the key looks like a typo.  For example: >
        require("gitflow").setup({ inline_blame = { enalbe = false } })
<   raises: >
        unknown option 'inline_blame.enalbe' (did you mean 'enable'?)
<   Highlight group names under `highlights` are free-form and never checked.

    Duplicate keybindings raise an error naming the mapping and every action
    bound to it, so a custom bind cannot silently shadow another feature.

6. COMMANDS                                                *gitflow-commands*

All commands use the `:Gitflow` prefix with tab completion.

UI ~
    :Gitflow help                       Show usage summary
    :Gitflow open                       Open the main panel
    :Gitflow refresh                    Refresh current panel
    :Gitflow close                      Close all Gitflow panels
    :Gitflow palette                    Open the command palette

Git ~
    :Gitflow status                     Open the status panel
    :Gitflow commit [--amend]           Create a commit
    :Gitflow push                       Push current branch
    :Gitflow pull                       Pull with configured strategy
    :Gitflow fetch [remote]             Fetch from remote
    :Gitflow sync                       Fetch + pull + push sequence
    :Gitflow diff [--staged] [path]     Open diff view
    :Gitflow log                        Open commit log panel
    :Gitflow stash list                 Open stash list panel
    :Gitflow stash push [message]       Stash changes
    :Gitflow stash pop                  Pop latest stash entry
    :Gitflow stash drop                 Drop latest stash entry
    :Gitflow branch                     Open branch list panel
    :Gitflow worktree [list|add|        Manage git worktrees
                   remove|move|lock|
                   unlock|prune]
    :Gitflow blame                      Open the git blame panel
    :Gitflow blame-inline               Toggle inline blame on current line
    :Gitflow merge <branch> [--abort]   Merge a branch
    :Gitflow rebase <branch>            Rebase onto a branch
                   [--abort|--continue]
    :Gitflow cherry-pick <commit>       Cherry-pick a commit
    :Gitflow conflicts                  Open conflict resolution panel
    :Gitflow quick-commit               Stage all + commit
    :Gitflow quick-push                 Stage all + commit + push

GitHub ~

    :Gitflow issue view <number>        View an issue
    :Gitflow issue create               Create a new issue
    :Gitflow issue comment <number>     Comment on an issue
    :Gitflow issue close <number>       Close an issue
    :Gitflow issue reopen <number>      Reopen an issue
    :Gitflow issue edit <number> [opts] Edit issue attributes
    :Gitflow pr list                    List pull requests
    :Gitflow pr view <number>           View a pull request
    :Gitflow pr create                  Create a new pull request
    :Gitflow pr comment <number>        Comment on a PR
    :Gitflow pr merge <number>          Merge a PR
    :Gitflow pr checkout <number>       Check out a PR branch
    :Gitflow pr close <number>          Close a PR
    :Gitflow pr review <number>         Open review panel for a PR
    :Gitflow pr submit-review <number>  Submit pending review

7. KEYBINDINGS                                          *gitflow-keybindings*

See |gitflow-config-keybindings| for the global mappings and how to move or
disable them, and |gitflow-config-panel-keybindings| for panel-local ones.

Discovering keys ~
    ?                   In any gitflow panel: open a scrollable help buffer
                        listing every key that panel binds.  The merge
                        conflict resolver uses c? instead, so plain ? stays
                        vim's reverse search in that editable pane.
    :Gitflow help       The same buffer for :Gitflow subcommands and the
                        global mappings currently installed.

Both are generated from the panel's own key registry, so they cannot drift
from what is actually bound.  KEYBINDINGS.md in the repository is the full
written reference.

Cross-panel rules ~
    r                   Refresh, in every panel.
    q                   Close, in every panel.
    ?                   Key help, in every panel.
    Destructive keys    d D x X H cD are delete/discard/rewrite verbs.  No
                        key that is destructive in one panel is a benign
                        action in another -- scripts/test_keymap_contract.lua
                        fails the build if that stops being true.  Every
                        destructive verb asks before it acts and declining
                        changes nothing; that is audited by hand, and
                        scripts/test_confirm_gates.lua drives three of the
                        gates with the answer NO.  Rebase's `d drop` is the
                        one deliberate exception: it edits a todo list you
                        have not executed yet.

                                                         *gitflow-keymaps-v2*
Migration from the pre-v2 keymaps ~

Global mappings.  Gitflow no longer claims any bare g-sequence that Neovim
itself defines: >

    Action              Old         New
    refresh             gr          <leader>gz    (gr is 0.11's LSP prefix)
    status              gs          <leader>gs    (gs sleeps)
    commit              gc          <leader>gc    (gc is the comment operator)
    diff                gD          <leader>gd    (gD goes to declaration)
    palette             gP          <leader>gx    (gP pastes)
    revert              gV          <leader>gv    (gV keeps the selection)
    tag                 gT          <leader>gt    (gT is previous tab)
    reflog              gF          <leader>gF    (gF edits file at line)
    rebase_interactive  gI          <leader>gI    (gI inserts at column 1)
    notifications       gN          <leader>gn    (gN is a text object)
<
Restore any of them with, for example: >lua
    require("gitflow").setup({ keybindings = { commit = "gc" } })
<
Panel keys.  The keys that changed meaning: >

    Panel               Old         New
    branch              r rename    e rename; r is refresh
    branch              R refresh   r refresh
    conflict list       A abort     X abort
    conflict list       R refresh   removed; r refreshes
    conflict resolver   cx reset    cD reset (cx opens the resolver from
                                    the status panel)
    reflog              R reset     H reset (soft/mixed/hard)
    issue list          X clear     F clear filters
    issue list          D in o/O/D  D on its own, and it confirms
    rebase (todo)       r reword    w reword
    rebase (todo)       d drop      d drop, confirmed by X execute
    review file list    dd delete   x delete
    every panel         ? searched  ? opens that panel's key help
                        backwards
<
Restore any of them per panel: >lua
    require("gitflow").setup({
      panel_keybindings = {
        conflict = { X = "A" },
        conflict_resolver = { cD = "cx" },
        rebase = { ["p/w/e/s/f"] = "p/r/e/s/f", r = "R" },
        status = { ["?"] = false },  -- ? back to reverse search
      },
    })
<

8. HIGHLIGHTS                                            *gitflow-highlights*

Override any highlight group via `setup({ highlights = { ... } })`.
Overrides fully replace the default definition for that group (they are
not merged). >lua
    require("gitflow").setup({
      highlights = {
        GitflowAdded = { fg = "#00ff00" },
        GitflowTitle = { bold = true, fg = "#ffffff" },
        GitflowBorder = { link = "FloatBorder" },
      },
    })
<

                                                    *gitflow-highlights-palette*
Accent Color Palette ~

Gitflow uses a background-dependent built-in accent palette selected by
`vim.o.background`:
  - `dark` background -> `PALETTE_DARK`
  - `light` background -> `PALETTE_LIGHT`

Palette values are defined in `lua/gitflow/highlights.lua` and can be
referenced from user highlight overrides:

    Name                Dark         Light        Used by ~

    accent_secondary    #DCA561      #B5651D      Palette header bar background
    separator_fg        #3E4452      #C8CCD4      Separator lines
    backdrop_bg         #000000      #E8E8E8      Palette backdrop overlay
    dark_fg             #222222      #222222      Palette header bar text
    log_hash            #E5C07B      #986801      Log commit SHA, diff file headers
    stash_ref           #C678DD      #A626A4      Stash ref, diff hunk headers

To change the accent colors for all related groups, override each
group individually: >lua

    require("gitflow").setup({
      highlights = {
        GitflowBorder  = { fg = "#98C379" },
        GitflowTitle   = { fg = "#98C379", bold = true },
        GitflowFooter  = { fg = "#98C379", italic = true },
      },
    })

9. SIGNS                                                      *gitflow-signs*

Git change indicators are displayed in the sign column for tracked files.
Signs update on `BufWritePost`, `BufEnter`, and after Gitflow operations.

Configure via `setup({ signs = { ... } })`: >lua
    require("gitflow").setup({
      signs = {
        enable   = true,    -- set false to disable
        added    = "+",     -- 1-2 cell string
        modified = "~",
        deleted  = "\u{2212}",
        conflict = "!",
        debounce = 300,     -- ms to wait after a write before refreshing
      },
    })
<

On Neovim 0.10+ signs use extmarks; older versions use `vim.fn.sign_place`.

`signs.debounce` coalesces a burst of rapid writes into a single git call
instead of one per write.

==============================================================================
10. ICONS                                                     *gitflow-icons*

When `icons.enable` is true (default), panels use Nerd Font glyphs for
state indicators. Set to false for ASCII fallback.

Configure via `setup({ icons = { ... } })`: >lua
    require("gitflow").setup({
      icons = {
        enable = false,   -- use ASCII indicators
      },
    })
<

Icon categories: git_state, github, branch, file_status.

11. STATUSLINE                                           *gitflow-statusline*

The plugin exports a statusline component that shows branch name, upstream
divergence (ahead/behind), and dirty-state indicator.

Native statusline: >lua
    vim.o.statusline = "%{%v:lua.require'gitflow'.statusline()%}"
<

lualine.nvim: >lua
    require("lualine").setup({
      sections = {
        lualine_c = { require("gitflow").statusline },
      },
    })
<

The statusline refreshes on `FocusGained`, `BufWritePost`, and after
Gitflow operations via the `User GitflowPostOperation` event.

12. LUA API                                                *gitflow-lua-api*

This is the surface a dependent plugin or user config can call directly, as
opposed to the panel/git/gh internals under `lua/gitflow/panels`, `git`, and
`gh`, which are implementation detail and may change without notice.

require("gitflow") ~
    setup({opts})   Initialize the plugin (see |gitflow-config|). Returns
                    the resolved `GitflowConfig`.
    get_config()    Returns the currently active resolved `GitflowConfig`
                    (the same table `setup()` returned).
    statusline()    Returns the current statusline string (see
                    |gitflow-statusline|). Safe to call before setup() has
                    finished; returns "" if not ready yet.
    initialized     `true` once `setup()` has completed.

require("gitflow.commands") ~
    register_subcommand(name, subcommand)
        Register a new `:Gitflow <name>` subcommand. `subcommand` is a
        table: >lua
            require("gitflow.commands").register_subcommand("my-thing", {
              description = "One-line summary shown in :Gitflow help",
              category = "Git",     -- optional, groups it in help output
              run = function(ctx)
                -- ctx.args:   full argv, ctx.args[1] == "my-thing"
                -- ctx.config: the resolved GitflowConfig
                return "Result message shown via vim.notify"
              end,
            })
<
        A throwing `run` is caught, reported via `vim.notify` with the
        original message and traceback preserved, and returned as the
        dispatch result — it never crashes `:Gitflow`.
